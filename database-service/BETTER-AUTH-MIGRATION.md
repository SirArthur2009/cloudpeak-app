# Better Auth cutover

The migration is opt-in. Supabase remains active until matching frontend and server configuration is deployed. Better Auth uses a private `cloudpeak_auth` schema in the existing Railway Postgres database. The data API continues to validate sessions and issue short-lived internal PostgREST tokens; existing UUIDs and Railway roles are retained. Storage validates Better Auth sessions through the data API. Public registration is disabled; existing administrator actions manage accounts.

1. Back up Railway and Supabase. Export `id,email,encrypted_password,email_confirmed_at,raw_user_meta_data,raw_app_meta_data,created_at` from Supabase `auth.users` to a private JSON array using a trusted SQL client. The user-list API does not include password hashes. Do not put this export in the repository or release bundle.
2. From `database-service`, run `node migrate-better-auth.js <absolute-private-export-path>` to validate without writes. Accounts without confirmed email or a bcrypt hash need separate review. Then run the same command with `--apply` against the intended Railway database. This creates the private schema and imports credentials; reruns do not overwrite changed passwords. No Supabase accounts are modified.
3. Set server `AUTH_PROVIDER=better-auth`, a random server-only `BETTER_AUTH_SECRET` (at least 32 characters), `BETTER_AUTH_URL=https://<portal-host>/railway-api/api/auth`, and `ALLOWED_ORIGINS` to the exact portal origins. Keep the secret stable across restarts. Better Auth serves `/api/auth` beneath the configured public base URL. The storage service also needs `AUTH_PROVIDER=better-auth` and its internal `DATA_API_URL`.
4. Build with `VITE_AUTH_PROVIDER=better-auth`, `VITE_DATA_API_URL=/railway-api`, `VITE_BETTER_AUTH_URL=/railway-api/api/auth`, and the existing Railway `VITE_STORAGE_API_URL`. Hosted bundle preparation sets these when `AUTH_PROVIDER=better-auth`. Retain the existing public Supabase URL/key for the data-client compatibility layer and old public photo URLs; Better Auth tokens cannot access Supabase RLS or Supabase Storage directly.
5. Verify a staging deployment: existing admin/client passwords, roles, forced password changes, account creation/deletion, owner updates, upload/download, logout, and a restart. Existing Supabase sessions do not transfer; users must sign in again using their unchanged passwords. Freeze account/password changes during the final export/import to avoid divergent credentials.
6. Deploy matching frontend and backend settings together. Keep Supabase available until the cutover is verified. Rollback requires redeploying with `AUTH_PROVIDER=supabase` and `VITE_AUTH_PROVIDER=supabase`; passwords changed or accounts created in Better Auth will not be reflected in Supabase. Plan reconciliation before rolling back.

Local testing can use `BETTER_AUTH_URL=http://127.0.0.1:3002`, `VITE_BETTER_AUTH_URL=http://127.0.0.1:3002/api/auth`, and exact localhost origins. Account writes still obey the existing `AUTH_WRITES_ENABLED` and `AUTH_ALLOWED_EMAILS` safeguards.

Run `npm run test:auth` for password-preserving login and session revocation checks. Run `npm run test:auth:postgres` for schema, account management, password changes, and session revocation against the configured isolated Railway test database. That integration test uses a temporary schema inside a rolled-back transaction. A deployed staging check is still required before production cutover. The private schema SQL is applied explicitly by the import command, never automatically at server startup.
